# GitHub Copilot Chat にローカルモデルを登録する(2026-10-19〜21)

## 目的

ストリーミング版の Qwen3.6-35B-A3B を OpenAI 互換の API サーバーとして常駐させ、VS Code の GitHub Copilot Chat から使えるか確かめる。

## 結論

- **登録はできた。** Copilot Chat のモデル選択欄から選べ、リクエストもサーバーに届いた。
- **実用にはならなかった。** Copilot は短い依頼にも約 2 万トークンのプロンプトを付ける。このモデルの prefill では 40 分前後かかり、途中で GPU のメモリが足りなくなって 2 回とも失敗した。
- 自走型のコーディングエージェントを目指すなら、Copilot に合わせるのではなく、この環境に合わせてプロンプトを作る方式(小さなシステムプロンプト、追記だけで伸びる会話)に切り替える。→ 次の実験へ。

## 構成

### API サーバー(`smoe/server.py`)

mlx-lm 付属の OpenAI 互換サーバー(`mlx_lm.server`)を流用し、モデルの読み込み部分(`ModelProvider._load`)だけを `load_streaming` に差し替えた。

- `/v1/chat/completions`(ストリーミング応答を含む)と、会話の共通部分の KV キャッシュ再利用は、mlx-lm のものをそのまま使う。
- リクエストのモデル名は無視し、起動時に指定した 1 モデルだけを常駐させる。
- 複数リクエストのまとめ処理は無効にした。ストリーミング層は 1 系列ずつの処理を前提にしているため。

```sh
uv run python -m smoe.server --model models/qwen3.6-35b-a3b-4bit-smoe \
    --cache-gb 2.45 --prefetch-m 8 --port 8080 \
    --chat-template-args '{"enable_thinking":false}'
```

curl での確認:短い質問(プロンプト 27 トークン)に 20〜24 秒で正しく答えた。

### Copilot Chat への登録

VS Code 1.142 では、Copilot Chat(0.70.0)が本体に同梱されている。自前のモデルは、言語モデルの設定ファイル `~/Library/Application Support/Code/User/chatLanguageModels.json` に、`customendpoint`(Custom Endpoint)の項目として書く。

```json
[
  {
    "vendor": "customendpoint",
    "name": "Local MoE (mlx-moe-streaming)",
    "apiKey": "local",
    "apiType": "chat-completions",
    "models": [
      {
        "id": "qwen3.6-35b-a3b-smoe",
        "name": "Qwen3.6-35B-A3B (local, SSD streaming)",
        "url": "http://localhost:8080/v1/chat/completions",
        "toolCalling": true,
        "vision": false,
        "thinking": false,
        "streaming": true,
        "maxInputTokens": 16384,
        "maxOutputTokens": 2048
      }
    ]
  }
]
```

- `apiKey` は必須項目なので、ダミーの値を入れる。
- **`toolCalling: false` だと、モデル選択欄に出てこない。** 「言語モデル」の一覧には出るが、Ask モードでも選べなかった。`true` にしたら選べるようになった。
- 設定ファイルは監視されていて、書き換えると再起動なしで反映された。

## 経過

### 1 回目(10-19 13:47):サーバーごと落ちた

- プロンプトは **19,517 トークン**あった。
- prefill を 8,192 トークンずつ処理しはじめたところで GPU のメモリが足りなくなり、プロセスごと落ちた。

一度に処理する幅とメモリの関係を、6,000 トークンのプロンプトで測った。

| 一度に処理する幅 | ピークメモリ | 所要時間 |
|---|---|---|
| 1,024 トークン | 4.86GB | 316 秒 |
| 2,048 トークン | 5.53GB(GPU 作業領域 約 5.4GB を超える) | 227 秒 |

→ サーバーの既定値を 1,024 にした。

### 2 回目(10-21 01:24〜02:06):「ファイルの存在確認」の依頼で、33 分後に失敗

| 時刻 | 出来事 |
|---|---|
| 01:24:21 | 1 本目のリクエスト(1,417 トークン)。prefill に約 4 分。会話のタイトル付けなどの補助的なリクエストとみる(推測) |
| 01:32:58 | 2 本目のリクエスト(**19,800 トークン**)。本体の依頼 |
| 01:38:54 | prefill の 1,024 トークン目まで |
| 01:39〜02:05 | 1,024 トークンあたり 1〜4 分のペース |
| 02:05:45 | 16,384 トークン目まで(開始から約 33 分) |
| その直後 | 17 回目の処理で GPU のメモリ不足。そのリクエストだけが失敗し、プロセスは残った |

- 文脈が長くなると、attention の一時メモリがそれに比例して増え、1,024 トークンずつでも上限を超えたとみる(推測)。計測中のスワップは 10GB に達していた。
- 途中まで進めた prefill の結果は保存されないので、失敗するとやり直しは最初からになる。

## 分かったこと

1. **Copilot のプロンプトは、依頼の重さに関係なく約 2 万トークンある。** システムプロンプト、ツールの定義、ワークスペースの情報が付くため。設定の `maxInputTokens` も守られなかった。
2. **この方式では、prefill の 1 回ごとにモデル全体をほぼ 1 回 SSD から読む。** 新しいトークンが数百個でも同じ。2 万トークンを 1,024 ずつ処理すると約 20 回読むことになり、外付け SSD では 40 分前後かかる。
3. **ツールを何度も呼んで進める使い方では、1 往復ごとにこの待ちが発生する。** Copilot の Agent モードのような使い方は成り立たない。
4. 逆に、会話の先頭が前回と同じであれば、その部分の計算結果は使い回せる。追記だけで伸びる会話にすれば、2 ターン目以降に読むのは増えた分だけになり、1 ターン 1〜2 分(外付け)に収まる見込み(机上の見積もり)。

## 次の実験

自走型のコーディングエージェント(リファクタリングやバグ修正を、時間をかけて自分で進めるもの)を、この環境に合わせて作る。

- 小さなシステムプロンプトで、ツールは bash だけにする。mini-SWE-agent が候補。
- 会話を追記だけで伸ばし、KV キャッシュの再利用を確実に効かせる。
- ツールの出力を短く切る。
- サーバー側では、文脈が長くなったら一度に処理する幅を自動で小さくする。

## 片付け

- サーバーは停止した(`pkill -f smoe.server`)。
- `chatLanguageModels.json` の登録は残してある。元の内容は空の配列で、同じディレクトリの `chatLanguageModels.json.bak-20261019114712` に退避してある。
