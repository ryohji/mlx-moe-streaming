# Qwen3.6-35B-A3B と Qwen3-Next-80B-A3B の比較(2026-10-16)

どちらも 4bit、外付け SSD(USB 10Gb/s、約 0.7GB/s)からストリーミング。M1 / 8GB。

## モデル

| | Qwen3.6-35B-A3B | Qwen3-Next-80B-A3B-Instruct |
|---|---|---|
| HF 公開 | 2026 年(Qwen3.6 系) | 2025-09-09 |
| repo | mlx-community/Qwen3.6-35B-A3B-4bit | mlx-community/Qwen3-Next-80B-A3B-Instruct-4bit |
| 層 / エキスパート / top-k | 40 / 256 / 8(共有 1) | 48 / 512 / 10(共有 1) |
| 1 エキスパート | 1.77MB | 1.77MB |
| experts.bin / 常駐部 | 18.12GB / 1.39GB | 43.49GB / 1.36GB |
| 1 トークンで触るエキスパート | 320 個 | 480 個 |

Qwen3.6 は画像入力つきモデルで、再配置時に画像側の重み(`vision_tower.*`)を捨てた。それ以外のコード変更なしで動いた。

## 速度(`bench/stream_bench.py`、生成 64 トークン × 2 プロンプト、先読み m = top-k)

| キャッシュ | Qwen3.6-35B | Qwen3-Next-80B |
|---|---|---|
| 2.45GB | 1.9 tok/s(ヒット率 55%) | 1.5 tok/s(60%) |
| 3.0GB | 2.1 tok/s(60%) | 1.7 tok/s(64%) |

## コーディング: HumanEval 20 問

`uv run python bench/humaneval.py --model models/<dir> --smoe --cache-gb 3.0 --prefetch-m <k> --n 20`

- 問題: HumanEval/0, 8, 16, 24, 32, 41, 49, 57, 65, 73, 82, 90, 98, 106, 114, 123, 131, 139, 147, 155(等間隔)
- 貪欲デコード、最大 512 トークン。Qwen3.6 は思考モードを切った(`enable_thinking=False`)。
- 採点は生成コードに HumanEval のテストを付け、別プロセスで実行(タイムアウト 10 秒)。

| | Qwen3.6-35B | Qwen3-Next-80B |
|---|---|---|
| **合格** | **18 / 20(90%)** | **19 / 20(95%)** |
| 不合格 | /32、/147(どちらも 512 トークンで打ち切り) | /32(512 トークンで打ち切り) |
| 生成トークン合計 | 4,139 | 2,082 |
| 所要時間(prefill 込み) | 53 分 | 47 分 |
| 生成速度(このタスク中) | 約 1.3 tok/s(prefill 込みの値) | 1.09 tok/s(生成のみ) |
| prefill 速度 | — | 3.7 tok/s |

- 合格数の差は 1 問で、20 問では統計的に区別できない。HumanEval は学習データに含まれている可能性が高く、どちらも上限に近い。
- 違いがはっきり出たのは**回答の長さ**。Qwen3.6 は docstring の書き写しや考察コメントで長くなり、合計トークンが 80B の約 2 倍。
  - そのため、トークンあたりは速いのに、課題全体の所要時間は 80B のほうが短かった。
  - /147 は 80B が 103 トークンで解き、Qwen3.6 は考察コメントの途中で上限に達した。
- 80B の生成速度が、このタスク中(1.09 tok/s)は速度ベンチ(1.7 tok/s)より遅い。prefill で 1 層あたり 512 個ほぼ全部を読み込んでキャッシュに入れ、生成で使うエキスパートを追い出してしまうためとみる(推測)。prefill で読んだものをキャッシュに入れない(または古い側に入れる)ようにすれば改善する見込みがある。

## 途中で直した不具合

80B は HumanEval の 5 問目(prompt 約 200 トークン)で GPU のメモリ不足になって落ちた。prefill で 1 層あたり約 512 個を一度に読んで積むため、一時的に約 1.8GB 余分に使っていた。
→ エキスパートを 32 個ずつ区切って「読む → 積む → 計算 → 評価」するチャンク処理を追加した(`smoe/layer.py` の `_chunked`)。一時メモリは約 110MB に収まる。OLMoE の一致テストは通過している。

## prefill とキャッシュ(区間別のヒット率)

`uv run python bench/phase_hits.py models/<dir> --cache-gb 3.0 --prefetch-m <k> [--prefill-admit all|none|tail] --out ...`

生成を「最初の 10 トークン」と「それ以降」に分け、ヒット率と速度を測った。プロンプトは HumanEval 4 問(/2, /12, /37, /101)と会話 2 本、最大 128 トークン。

### 主因はコード生成のヒット率の低さだった

| モデル | プロンプト | 最初の 10 トークン | それ以降 | 生成速度(それ以降) |
|---|---|---|---|---|
| Qwen3.6-35B | コード | 60〜69% | 56〜60% | 1.3〜1.5 tok/s |
| Qwen3.6-35B | 会話 | 69〜78% | 81〜82% | 2.9〜3.1 tok/s |
| Qwen3-Next-80B | コード | 53〜64% | 49〜62% | 0.9〜1.2 tok/s |
| Qwen3-Next-80B | 会話 | 64〜73% | 69〜77% | 1.6〜1.9 tok/s |

- 「prefill がキャッシュを流すので生成が遅い」という仮説は**外れ**。生成の頭のヒット率は、それ以降と同じか高い。
- 遅さの主因は、**コード生成ではヒット率自体が会話より 15〜25 ポイント低い**こと。速度はほぼ半分になる。両モデルとも同じ傾向。
- 速度ベンチ(`stream_bench.py`)は会話プロンプトなので、コード課題中より速く出る。

### prefill で読んだものの扱い(Qwen3.6、`--prefill-admit`)

| 方式 | 内容 | prefill(コード) | 最初の 10 トークンのヒット率 | 11 トークン目以降 |
|---|---|---|---|---|
| all(従来) | 読んだものを全部キャッシュに入れる | 22.1〜25.5 秒 | コード 60〜69% / 会話 69〜78% | 基準 |
| none | 入れない(既存の中身は使う) | 18.6〜20.9 秒 | コード 58〜73% / 会話 67〜76% | **3 方式で同一** |
| tail | プロンプト末尾 16 トークンが使ったものだけ入れる | 20.1〜21.9 秒 | コード 62〜71% / 会話 72〜81% | **3 方式で同一** |

- 11 トークン目以降のヒット率は、3 方式で小数点以下 3 桁まで同じ。違いが出るのは生成の最初の 10 トークン前後だけで、その後は生成自体が読んだエキスパートでキャッシュが同じ状態に収束する。
- tail が最も安定してよい(最初の 10 トークンで +0〜3 ポイント)。prefill も 10〜15% 速くなる(キャッシュの出し入れが減るため)。**既定を tail にした。**
- ただし、効くのは生成の頭だけなので、課題全体の時間への効果は小さい。
