# Phase 3(前半): 読み出し経路と先読み

計測日 2026-10-16。開始時のスワップ 2.7GB(VSCode 起動中)。Qwen3-30B-A3B、キャッシュ 2.45GB 固定、
生成 64 トークン × 2 プロンプト。**同じ設定の再計測で ±0.3 tok/s(1 割強)ぶれる**ので、それ未満の差は判定しない。

## 1. 断片化の解消(効果大)

再配置ツールは `experts.bin` をシャードの順にあちこちへ `pwrite` するため、APFS 上で 1 ブロブが細かい断片に散らばっていた。
1 ブロブの読み出しが、小さなランダム読みの連続になっていた。

- 対策: 書き込み前に `F_PREALLOCATE`(`F_ALLOCATECONTIG`)で連続領域を確保する(`tools/repack.py`)。
- 再現: `uv run python bench/read_path.py <dir>`(1 層ぶんのミスを並列に読む操作の GB/s)

| ファイル | batch 4 / 1 スレッド | batch 4 / 4 スレッド | batch 8 / 4 スレッド |
|---|---|---|---|
| Qwen3 3bit(断片化) | 0.84 | 1.29 | 1.72 |
| Qwen3 3bit(dd で書き直し) | 2.05 | 2.30 | 2.32 |
| Qwen3 4bit(連続確保で再配置) | 1.80 | 1.84 | 2.32 |
| OLMoE(断片化) | 1.48 | 2.10 | 2.76 |
| OLMoE(連続確保) | 2.06 | 3.07 | 3.68 |

(単位 GB/s)

- 生成速度は、先読みなしで 4bit が 2.0 → 2.4 tok/s、3bit が 2.5 → 3.2 tok/s(+20〜28%)。
- 使い回しバッファへの `preadv` も効く(新規確保の `pread` より 1〜2 割速い)が、断片化に比べれば小さい。
- 配列化(numpy → mx.array + eval)は 7.3GB/s で律速ではない。

## 2. 1 層先の先読み

層 l のルーティングが確定した時点で、層 l のブロック入力に層 l+1 のルーターを当て、上位 m 個のうちキャッシュに無いものを裏のスレッドで読む。

`uv run python bench/stream_bench.py <dir> --cache-gb 2.45 --max-tokens 64 --prefetch-m 8`

| 設定 | 4bit tok/s | 3bit tok/s | 埋まったミス | 無駄読み |
|---|---|---|---|---|
| 先読みなし | 2.4 | 3.2 | — | — |
| m=8 | 2.5 / 2.8(2 回) | 3.9 / 3.8(2 回) | 58〜63% | 21〜26% |
| m=12 | 2.4 | 3.8 | 67〜71% | 48〜52% |
| m=12、early | 2.0 | 3.7 | 67〜71% | 48〜52% |
| m=16、early | 1.9 | 3.2 | 69〜73% | 65〜67% |
| m=8、外れも保持 | 2.5 | 3.9 | 58〜63% | 20〜24% |
| m=12、外れも保持 | 2.1 | 3.2 | 68〜71% | 46〜48% |

- 「early」は、層 l のミスを読むより先に先読みを発行する設定。「外れも保持」は、外れた先読みを捨てずにキャッシュへ入れる設定。
- **m = k(8)で遅延発行が最良。** 3bit で +20%、4bit で +4〜17%(ばらつきの範囲と重なる)。
- 予測を増やす(m=12、16)と、無駄読みが帯域を食って相殺か逆効果になる。
- early は、層 l のミスの読み出しが先読みの後ろに並ぶため遅くなる。
- 外れた先読みをキャッシュに残しても、ヒット率は上がらなかった。

## 2b. ゼロコピー読み込み

MLX の配列(CPU ストリームで確保した uint8)のメモリへ、`preadv` で直接読む。
部品はスライスと `view` で切り出すので、numpy 経由のコピー(約 440MB/トークン、7.3GB/s で約 60ms)が無くなる。
`memoryview(mx 配列)` が書き込み可能で、スライスもバッファを共有することは確認済み。

| | 4bit | 3bit |
|---|---|---|
| 先読み m=8(コピーあり) | 2.5〜2.8 | 3.8〜3.9 |
| + ゼロコピー | 3.2〜3.3 | 4.3〜4.7 |

(キャッシュ 2.45GB、tok/s)

## 2c. 層ごとの同期のコスト

OLMoE(全部メモリに載る)で切り分けた。単位は tok/s。

| 条件 | 生成 tok/s |
|---|---|
| 素の mlx-lm | 71.1 |
| 素の mlx-lm + 層ごとに `np.array(indices)` で同期 | 26.4 |
| ストリーミング版、全部キャッシュ済み(個別演算) | 22.6 |
| 同上、使う分を積んで gather_qmm | 16.9 |

- **オーバーヘッドの主因は同期そのもの**(1 回あたり約 1.5ms)。自前の Python 処理は 1 層あたり約 0.4ms にすぎない。
- MLX は遅延評価なので、同期と同期の間に CPU がグラフを組み立てている間、GPU が止まっている。

対策と効果:

| 対策 | 内容 |
|---|---|
| `mx.async_eval` | MoE 出力を組み立てた直後に GPU へ投げ、次の層の attention を CPU で組み立てる間に計算を進める。OLMoE の全キャッシュ時で 22〜23 → 26〜28 tok/s |
| 予測を同じ評価に混ぜる | 先読みの予測を層の入口でグラフに積み、ルーティングと同じ 1 回の評価で確定させる。予測のための追加同期が無くなる |

Qwen3 での結果(先読み m=8、tok/s):

| 版 | キャッシュ | ゼロコピーまで | + 同期削減 |
|---|---|---|---|
| 4bit | 2.45GB | 3.2〜3.3 | **3.5 / 3.5** |
| 3bit | 2.45GB | 4.3〜4.7 | **4.8 / 4.6** |
| 4bit | 3.26GB | — | **3.8**(MLX ピーク 4.36GB) |

4bit は時間の 54% が読み出し待ちで、その間の実効は約 3GB/s(SSD の上限付近)。
**ここから先は、読む量を減らす(ヒット率、容量、ビット数)ほかない。**

## 3. いまの時間の内訳(机上)

4bit・m=8・2.8 tok/s で、1 トークン約 360ms。

- **ミスの読み出し**: 約 440MB/トークン。2.3GB/s で約 190ms。
- **計算と同期**: 残り約 170ms。層ごとにルーティングを確定させる同期が 48 回入る。

4bit が先読みであまり伸びないのは、1 層ぶんの計算(約 3.5ms)の間に 1 層ぶんのミス(約 9MB、約 4ms)を読み切れないため(推測)。

## 次の候補

1. **読む量そのものを減らす**: キャッシュの方針(LRU 以外)と容量。Belady との差は 20 ポイントある(Phase 1)。
2. **同期のオーバーヘッドを減らす**: OLMoE の全キャッシュ時で素の 0.42 倍。デコード 1 トークンの計算を MLX のグラフにまとめる、Python 側の処理を減らす。
3. **2 層先まで先読みする**: 読み出しを途切れさせない。ただし d=2 の recall@k は 73%(OLMoE)で、無駄読みが増える。

## 4. 層ごとの LRU(実機)

`--per-layer`(層ごとに容量を等分)を、4bit で交互に 2 回ずつ、3bit で 1 回ずつ測った。キャッシュ 2.45GB、先読み m=8。

| 版 | 全体 LRU | 層ごとの LRU |
|---|---|---|
| 4bit | 3.4 / 3.1 tok/s(ヒット率 54.4%) | 3.4 / 3.2 tok/s(56.4%) |
| 3bit | 4.6(61.4%) | 4.3(61.6%) |

ヒット率は少し上がるが、速度はばらつきの範囲内。既定は全体 LRU のままにする。

最初の実装は、prefill で 1 層が全エキスパートを使うと層ごとの上限まで減らせず、総量が容量を超えて GPU のメモリ不足で落ちた。
総量は常に全体 LRU で容量内に戻すよう直した。

## 5. 投機デコード(Phase 4 の試行、mlx-lm 標準の実装をそのまま使用)

ドラフトは mlx-community/Qwen3-0.6B-4bit(0.35GB)。4bit、キャッシュ 2.45GB、先読み m=8。

`uv run python bench/stream_bench.py models/qwen3-30b-a3b-4bit-smoe --cache-gb 2.45 --prefetch-m 8 --draft mlx-community/Qwen3-0.6B-4bit --num-draft N`

| ドラフト数 | 生成 tok/s | ドラフト由来のトークン | ヒット率 | 読み出し MB/トークン |
|---|---|---|---|---|
| なし | 3.1〜3.5 | — | 54% | 440 |
| 1 | 2.2 | 38% | 48% | 418 |
| 2 | 2.2 | 52% | 45% | 437 |
| 3 | 1.7 | 59% | 28% | 597 |

- **そのままでは逆効果。** 1 トークンあたりの読み出し量はドラフト 1〜2 で変わらないので、遅くなった原因は I/O ではない。
- 原因の推測(未計測):
  - 検証時(2〜4 トークン)は、使うエキスパートを積み直すコピー経路を通る。
  - 検証時は先読みが効かない。
  - ドラフトモデル側の同期が加わる。
- 伸ばすには次が要る。
  - 少数トークン用の個別演算経路(トークンをエキスパートごとに振り分けて掛ける)
  - 検証時の先読み(複数トークンの予測の和集合)
  
  効果は未知数。
