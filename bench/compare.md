# 既存の実行方法との比較(2026-10-16)

M1 / 8GB / macOS 27.0.1。VSCode 起動中、計測開始時のスワップ 1.6〜4GB。
ストリーミング版以外のモデルファイルは、計測後に削除した(ディスク節約のため)。

| **ストリーミング版(本実験)** | Qwen3-30B-A3B 4bit、キャッシュ 2.45GB | **3.5** | 3〜4 | 動く。MLX ピーク 3.55GB |
| **ストリーミング版(本実験)** | 同、キャッシュ 3.26GB | **3.8** | — | 動く。MLX ピーク 4.36GB |

## 読み取れること

- **8GB 機で Qwen3-30B-A3B を動かせる既存の方法は、llama.cpp の CPU 実行(mmap)だけだった。** 本実験の方式はその **3〜5 倍**速い(3.5〜3.8 vs 0.7〜1.3 tok/s)。
- 素の mlx-lm と、llama.cpp の GPU 実行は、どちらもメモリ不足で動かない。
- llama.cpp の MoE オフロード(エキスパートを CPU 側に置く機能)は動いたが 0.05 tok/s で、この機体ではまったく実用にならない。
- 一方、**dense の Qwen3-8B 4bit は 13.4 tok/s で、本実験の約 4 倍速い。**
  - 品質(簡易 perplexity)は、30B-A3B 4bit に対してコードは同等、日本語は 9%、英文は 7% 劣る程度。
  - 評価トークンが少ないので断定はできないが、**速度と品質の釣り合いでは 8B が有利**に見える。30B-A3B を選ぶ理由になるほどの品質差は、この簡易評価では確認できていない。

## 注意

- llama.cpp の数値は llama-bench の短い計測(32〜64 トークン)。ページキャッシュの状態でばらつく(64 トークンで 0.70〜1.29 tok/s)。
- llama.cpp は Q4_0(4.5bit 相当)、本実験は MLX の 4bit(group 64、約 4.5bit 相当)。ビット数はほぼ同じだが、量子化方式は異なる。
- 品質比較は簡易 perplexity だけ。タスク性能(コード生成の正答率など)は測っていない。
